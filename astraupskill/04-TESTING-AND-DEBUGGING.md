# Testing and debugging the boundary

The regression test [`comment-delete-boundary.test.mjs`](../tests/comment-delete-boundary.test.mjs) uses `loadTypeScript` to evaluate the actual staged repository source. It stubs only `./prisma`; no repository algorithm is reimplemented in the test. A mutable proxy lets each test replace the Prisma double after the module is loaded. This matters because a copied "expected implementation" could pass while production code stayed broken.

The first case returns an owned comment and asserts true. It compares serialized call records so VM-created objects do not fail Node's cross-realm prototype check. The expected query includes both `id` and nested `article.slug`; the expected write is exactly `{ where: { id } }`. The second case represents a wrong parent by returning null. It asserts false and an empty delete list, which checks the important zero-write boundary. The third case returns a matching row owned by another user and expects `Forbidden` with no write. The fourth loads `articles.ts`, captures the registered nested DELETE callback using a router double, and executes it with the real repository. It checks the passed slug, 204/404/403 outcomes, success-only deletion, and forwarding of the exact delete error to `next`.

When debugging a failure, inspect the first call before inspecting the result. If `findFirst` receives only `{ id }`, the repository fix is absent. If it receives the slug but the delete list is nonempty for null, the guard is misplaced. If the repository test passes but the handler assertion fails, the method signature changed without wiring. Run from the staged project with `node --experimental-vm-modules --test tests/comment-delete-boundary.test.mjs`; the captured check is `crud-b03-astra-runtime2`. The evidence reports four passing subtests. It does not prove Prisma SQL, Express middleware, or transaction behavior.


The test's explicit doubles also reveal failure handling: `findFirst` is the authorization and identity read, while `delete` is the only write. Keeping those call logs separate makes a "returned false but still deleted" regression visible. This is a meaningful runtime check even though it stops before a real database driver.
