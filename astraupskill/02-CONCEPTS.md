# Concepts: nested identity and authorization

A nested CRUD URL carries two facts: the parent identity (`slug`) and the child identity (`id`). The safe lookup is therefore the conjunction `comment.id = id AND article.slug = slug`. Checking only the child id answers a different question, "does this row exist anywhere?", and lets the URL lie about its parent. This matters even when the user owns the comment: ownership answers who may act, while parent matching answers which resource they asked for.

The repository applies these checks in a deliberate order. `findFirst` returns no row for a wrong slug, so the route emits 404 and never reaches `comment.delete`. If the row matches the article but its `authorId` differs, the repository throws `Forbidden`, which the route maps to 403. If both match, the delete operation uses the id as Prisma's unique key. The write still uses only the id after that guarded read. This demonstrates the sequential path, but does not atomically preserve the read conditions if another operation changes the relationship or author before deletion. Conditional writes and database isolation require a separate design and test.

The distinction between 404 and 403 is a product decision visible in the existing route. Preserve it rather than inventing a new error shape. Likewise, do not claim tenant isolation: this schema has article ownership and comment authorship, but no organization predicate in the changed method. A review should ask whether every argument from the URL reaches the repository, whether a wrong parent causes zero writes, and whether the old ownership rule remains intact. Those questions are answered by the four tests, while real Prisma behavior and Express middleware remain stated limitations.
