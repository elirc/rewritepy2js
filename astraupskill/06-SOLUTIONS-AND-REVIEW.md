# Solutions and review rubric

For practice case 1, the lookup predicate is `{ id: 9, article: { slug: 'alpha' } }`. The row matches the caller, so the repository invokes `comment.delete({ where: { id: 9 } })` and returns true; the route ends 204. Case 2 returns false because the relation-aware lookup finds no comment under `beta`; the route sends 404 and performs zero writes even though the caller owns the alpha comment. Case 3 throws `Forbidden`; the existing route catch maps that exact error to 403. Case 4 returns false and does not call delete. Case 5 is outside the patch: the route's existing `parseInt` behavior and any validation middleware need a separate regression if malformed ids are to be tightened.

A reviewer should award credit when the change passes the slug from route to repository, uses the real schema relation name, preserves ownership, and proves a wrong parent causes zero writes. Ask for a requested-change test and an ownership test; one happy path is insufficient. Check that the baseline snapshots are exact, that changed source is listed in the spec, and that the test imports production source through the helper. Reject claims of PostgreSQL or end-to-end coverage because the test supplies Prisma, Express router, middleware and response doubles instead of mounting an Express server.

The remaining limitation is concurrency: a read followed by delete is not an atomic authorization statement. A later hardening could use a transaction or a compound delete condition if supported by the schema, but that would require explicit database evidence. Also avoid calling this tenant isolation; the examined model has article and author relationships, not an organization key. The implementation is successful because it restores the nested resource invariant with the smallest observable surface.
